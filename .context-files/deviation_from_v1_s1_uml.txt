PURPOSE

This document records differences between the original Stage 1 UML class
diagram and the implemented Stage 1 Java application.

The original UML is preserved as a design baseline. Changes made during
implementation are documented here with their rationale.

Reference documents:
- design_choices.txt
- v1 stage1 uml class diagram.txt
- SC2002 Restaurant Rush Group Assignment brief

Stage 1 includes:
- 18-turn game simulation
- Customer arrivals, seating and waiting queues
- Ordering, preparation, serving and eating
- Automatic cashier payment
- Satisfaction reduction and customer abandonment
- Revenue and performance tracking
- Victory/defeat evaluation
- Interactive command-line interface

The original UML already contains the separation between GameController
and TurnProcessor, as well as the typed WaiterChoice subclasses.
These are implemented design features, NOT deviations.

================================================================================
A. INTENTIONAL DESIGN DEVIATIONS
================================================================================

A1. GAME RESULT CHECK PLACEMENT

Original UML:
- GameController exposes checkResult() : GameResult.
- GameState stores the statistics needed for victory evaluation.

Implementation:
- GameState implements checkResult().
- GameState also provides isGameOver().
- GameController.checkResult() delegates to GameState.

Rationale:
- GameState owns revenue, paid-customer counts and satisfaction totals.
- Keeping result evaluation close to the relevant data improves cohesion.
- GameController remains responsible for coordinating game flow.

A2. ADDITIONAL DEFEAT-CAUSE REPORTING

Original UML:
- GameResult contains VICTORY and DEFEAT.
- Detailed defeat-cause reporting is not shown.

Implementation:
- GameState provides getDefeatCauses() : List<String>.
- Supporting checks evaluate the individual victory requirements.
- The CLI can display the reasons for defeat.

Rationale:
- A game may fail more than one victory requirement.
- Reporting the unmet requirements gives the player useful feedback.
- GameResult remains a simple VICTORY/DEFEAT enumeration.

A3. ACTION VALIDATION AND ERROR MESSAGES

Original UML:
- executeWaiterChoice(choice) : boolean
- executeChefChoice(orderId) : boolean
- Validation methods return boolean.

Implementation:
- The corresponding execution and validation methods return String.
- null indicates success or a valid choice.
- A non-null String explains why the action was rejected.

Rationale:
- Invalid decisions should be explained clearly to the player.
- The CLI can display the returned error message.
- Invalid choices do not consume the relevant staff action.
- The manager can select another valid action.

A4. ORDER STORES CUSTOMER IDENTIFIER

Original UML:
- Order contains orderId, item, status, remainingUnits,
  finalPriceCents and readyTurn.
- No customerId attribute is shown.

Implementation:
- Order also stores an immutable customerId.

Rationale:
- Orders can be associated with their customers without storing
  an additional Customer object reference.
- The CLI can identify the customer associated with each order.
- ServeChoice can resolve the order's customer efficiently.

A5. CUSTOMER SEATING AND WAITING QUEUE MANAGEMENT

Original UML:
- Customer has a status and an associated order.
- Table stores its occupant.
- GameState owns the waiting queue.

Implementation:
- Customer additionally stores its assigned Table.
- Customer provides getTable() and seatAt(Table).
- GameState provides removeWaitingCustomer(Customer).
- Waiter.seat() delegates seating to the Customer operation.

Rationale:
- Seating must update customer status and table occupancy consistently.
- Customer state changes are encapsulated rather than exposing
  a public setStatus() operation.
- GameState retains control over the waiting queue.
- Collection getters expose read-only views to callers.

A6. DETERMINISTIC CUSTOMER FOOD CHOICE

Original UML:
- CustomerChoiceGenerator provides chooseItem(menu, customer).
- The exact deterministic selection rule is unspecified.

Implementation:
- The menu index is selected using:

  index = (customerId - 1) % menuSize

- Customers select from the fixed menu in a repeating sequence.

Rationale:
- Customer choices are predictable and reproducible.
- Automated tests can verify expected orders.
- The player does not directly select customers' food.

A7. ORDER FINAL PRICE MODIFICATION

Original UML:
- Order contains finalPriceCents.
- A setter for this attribute is not shown.

Implementation:
- finalPriceCents initially equals the selected MenuItem base price.
- Order provides setFinalPriceCents(int).

Rationale:
- The order's charged amount can be changed independently of
  the immutable menu-item base price.
- This supports future pricing rules without changing MenuItem.
- Stage 1 uses the normal menu prices.

================================================================================
B. IMPLEMENTATION DETAILS AND COMPLETED FUNCTIONALITY
================================================================================

The following items were previously documented as incomplete or as
temporary stub-related deviations. They are now implemented for Stage 1.

B1. GAMECONTROLLER AND TURNPROCESSOR

- GameController coordinates the turn sequence and player decisions.
- TurnProcessor handles automatic end-of-turn updates.
- Customer arrivals follow turns 1, 4, 7, 10, 13 and 16.
- The game has exactly 18 turns.
- Victory is evaluated at the end of turn 18.

This separation is consistent with the original UML.

B2. WAITER ACTIONS

The Waiter supports:
- WAIT
- SEAT
- TAKE_ORDER
- SERVE

The implementation validates action-specific targets and relevant
customer, table and order states.

A maximum of one valid Waiter action may be performed per turn.
Invalid actions do not consume the action allowance.

The original UML's typed choice classes are retained:
- WaitChoice
- SeatChoice
- TakeOrderChoice
- ServeChoice

B3. CHEF PREPARATION

- Chef preparation is implemented.
- The Chef performs at most one preparation unit per turn.
- Salad requires 1 preparation unit.
- Burger requires 1 preparation unit.
- Pasta requires 2 preparation units.
- Orders can be prepared on the turn they are placed.
- An order that becomes READY cannot be served until a later turn.

B4. CASHIER PAYMENT

- Cashier payment processing is implemented.
- Payment is handled automatically during end-of-turn processing.
- At most one eligible customer pays per turn.
- Eligible customers are processed in arrival order.
- Payment cannot occur in the same turn the customer becomes
  READY_TO_PAY.
- Successful payment updates revenue and paid-customer statistics.
- The customer's table is freed after payment.

B5. CUSTOMER LIFECYCLE

Customer lifecycle methods are implemented, including:
- Satisfaction reduction
- Abandonment detection
- Seating
- Order assignment
- Serving
- Eating completion
- Payment completion

Customers begin with satisfaction 100.

Waiting or seated customers who have not been served lose
8 satisfaction points per turn, with a minimum of 0.

A customer who reaches 0 satisfaction before being served
leaves the restaurant. Any unfinished order is cancelled,
and the occupied table, if any, is freed.

Unhappy departures are recorded in GameState.

B6. MENU AND MENUITEM

The fixed Stage 1 menu is implemented:

- Salad: 900 cents, 1 preparation unit
- Burger: 1500 cents, 1 preparation unit
- Pasta: 1800 cents, 2 preparation units

MenuItem validates its constructor inputs.

The menu implementation supports the Stage 1 ordering workflow.

B7. TABLE OPERATIONS

Table operations are implemented:
- occupy()
- free()
- isAvailable()
- getOccupant()
- getTableId()

The restaurant has two tables.

Table availability and occupancy are integrated with seating,
abandonment and payment.

B8. COMMAND-LINE INTERFACE

The playable Stage 1 entry point is:

  game.RestaurantRushCLI

The original UML models a RestaurantCLI boundary class and a
separate Main entry point.

The implemented application uses RestaurantRushCLI as the
playable command-line entry point. This is an implementation
structure difference from the original UML.

The CLI displays:
- Current turn
- Revenue
- Paid and served customer counts
- Average paid-customer satisfaction
- Waiting customers
- Occupied and available tables
- Customer and order information
- Available manager decisions
- Final victory/defeat result

When no customer has paid, the CLI displays average satisfaction
as N/A rather than showing 0.00.

The numeric GameState average remains a double; the N/A display
is handled by the CLI.

B9. TEST HARNESS AND AUTOMATED TESTS

The original UML does not model test classes.

Additional testing components include:
- harness.Stage1TurnSequenceHarness
- game.ControllerSimulationTest
- game.Stage1RegressionTest
- game.Stage1EdgeCaseTest

The legacy harness is retained for development/testing purposes.
It is not the primary playable application.

The Stage 1 regression and edge-case suites have passed
21 tests in total.

These tests cover:
- Initial game state
- Customer arrival schedule
- Seating and ordering
- Waiter and Chef action limits
- Invalid action handling
- Preparation and serving restrictions
- Eating and payment timing
- Table reuse
- Customer abandonment
- Read-only collections
- 18-turn game completion
- Victory and defeat outcomes

ADDITIONAL STAGE 1 IMPLEMENTATION NOTES

1. Customer.setStatus(CustomerStatus) is public in the current
   implementation. TurnProcessor uses it when marking abandoned
   customers as LEFT. This differs from the original intention
   to restrict status changes to lifecycle methods.

2. Waiter.takeOrder(Customer, Order) returns void. The
   GameController creates the Order and adds it to GameState.
   The Waiter validates and assigns the existing Order to
   the Customer. This keeps order creation and storage in
   GameController rather than Waiter.

3. The original cli.Main and cli.RestaurantCLI files remain
   as unimplemented placeholders. The playable Stage 1
   application is game.RestaurantRushCLI.
