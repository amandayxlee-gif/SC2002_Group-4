================================================================================
A. INTENTIONAL DEVIATIONS
================================================================================

A1. GameResult CHECK PLACEMENT
    - UML shows checkResult() : GameResult on GameController. Implemented as
      GameState.checkResult() (plus GameState.isGameOver()) with
      GameController.checkResult() delegating. Why: GameState holds every
      statistic the check needs (design_choices.txt section 3.4). Diagram can
      add the delegation dependency when it is next revised.

A2. DEFEAT CAUSE REPORTING ADDED (GameState.getDefeatCauses)
    - Not in the UML: GameState gains getDefeatCauses() : List<String> plus
      private helpers hasEnoughPaidCustomers/hasEnoughRevenue/
      hasEnoughSatisfaction, shared with checkResult(). Why: an invalid run
      can miss several victory targets at once, so causes are a list shown
      after a plain VICTORY/DEFEAT result; GameResult itself stays
      {VICTORY, DEFEAT} so callers keep simple "if defeat" checks. CLI shows
      causes after result.

A3. CHOICE METHODS RETURN String INSTEAD OF boolean
    - executeWaiterChoice, executeChefChoice, validateWaiterChoice and
      validateChefChoice now return String: null = executed / valid, otherwise
      the failure reason. Why: an invalid choice must explain why it failed
      (assignment doc section 3.4). Returning the reason from the public
      execute methods (not just the private validators) is what lets the CLI
      display it via displayError before the manager redecides.

A4. Order GAINS AN IMMUTABLE customerId
    - Not in the UML attribute list. Set once in the constructor, no
      back-reference to the Customer object. Why: lets the UI display and sort
      orders by customer, and lets ServeChoice(orderId) resolve ownership
      without traversing customers; avoids the sync cost of a bidirectional
      association.

NOTE (not a design choice): HARNESS FILE ADDED
    - harness.Stage1TurnSequenceHarness exists purely as a temporary testing
      feature: it verifies the 18-turn loop, the arrival schedule and the
      result/defeat-cause check. It is not a design decision and can be
      removed or replaced by the CLI once Person 5 lands it.

================================================================================
B. DEVIATIONS DUE TO INCOMPLETE TODO/STUBS
   (each entry disappears or is replaced when the owning package lands)
================================================================================

B1. STUB CLASSES WITH TODO BODIES (Customer, Order, Waiter, Chef, Cashier,
    CustomerChoiceGenerator, RestaurantCLI, Main)
    - Current scope covers only the turn controller and sequence. The stubs
      carry the UML's method signatures (with GAP/TODO comments) so the
      skeleton compiles and runs, and teammates can fill bodies without
      signature changes.

B2. VALIDATION STUBS ALWAYS RETURN NULL (VALID)
    - GameController.validateWaiterChoice and validateChefChoice return null
      (valid) for now. Why: validation rules depend on waiter/kitchen logic
      outside the current scope; the validate-then-execute-immediately
      structure and the String reason contract are in place, so only the rule
      bodies need dropping in later.

B3. WAITER EXECUTION IS A NO-OP
    - GameController.executeValidWaiterChoice does not dispatch to the Waiter
      yet. Why: Waiter.seat/takeOrder/serve bodies are Person 3 TODOs.

B4. Menu SEEDED WITH THE THREE BASE ITEMS
    - Menu is a Person 4 stub but is constructed with Salad 900c/1, Burger
      1500c/1, Pasta 1800c/2 (assignment doc section 2.1). Why: needed for any
      runnable pass; treat seeding as placeholder until the menu work package
      lands.

B5. AVERAGE SATISFACTION DOES NOT DISTINGUISH "NO PAYMENTS" FROM 0.0
    - GameState.getAverageSatisfaction() returns 0.0 when paidCount = 0; the
      model has no N/A representation. The UML note expects the average to be
      displayed as N/A when nobody has paid; that mapping is deferred to the
      CLI and may change when it lands (assignment doc section 3.5).

B6. Table IMPLEMENTED IN FULL WHILE SURROUNDING CLASSES ARE STUBS
    - occupy/free/isAvailable work, unlike the other Person 3 stubs. Why:
      GameState owns the two tables and the seat/free flow needs them. The
      implementation is deliberately only as complex as the stub flow
      requires; Person 3 may reshape it when the staff package lands.
